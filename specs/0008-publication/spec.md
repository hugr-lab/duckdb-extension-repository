# Spec 0008: Publication and promotion

- **Status**: phase 1a implemented (publication, promotion, reserved names, blocks); 1b and 2 next
- **Date**: 2026-10-08
- **Author**: vgsml, Claude

## Summary

Builds reach channels over the API, not only through `kista admin release add` on the server:

- **publishing** uploads a built extension into a channel. The server checks that the file is what
  it claims to be: its footer against the declared version and platform, and its name against the
  init symbol the binary exports for DuckDB to load;
- **promotion** releases Builds that are already in one channel in another, with that channel's
  signature: one release, or a whole extension version on every platform at once;
- names DuckDB ships (core) or lists (community) are **reserved**: publishing or promoting one takes
  grants that name it;
- a tenant administrator can **block** a body hash: its releases are yanked and it is not released
  again;
- a **publisher** is an identity that may only publish and promote: CI through **trusted
  publishing** (GitHub Actions OIDC, bound to immutable repository and owner ids and to a workflow),
  and, in phase 2, **API keys**. People publish with their tenant tokens.

Delivery is phased:

1. **Publication and trusted publishing**: the `publish` and `promote` verbs; upload, promotion and
   block; the file checks; reserved names; publishers with GitHub credentials. This serves hugr's
   own CI and promoters, our builds of core extensions, and organisations whose CI is on GitHub.
   Delivered in two pull requests: **1a**, everything but publishers (people publish with tenant
   tokens), and **1b**, publishers and trusted publishing (migration 0006).
2. **API keys**: publisher credentials for CI without OIDC and for Enterest's external publishers.

This spec amends earlier specs (see "Changes to earlier specs").

## Problem

- **hugr's own CI** builds duckdb-acl, acl_otel, tresor and hugr_node in GitHub Actions. Today an
  operator with a shell on the server copies each file and runs `kista admin release add`. CI should
  publish into `staging` itself, with no stored secret, and a release manager should promote a
  tested version to `prod` across every platform at once, neither of them holding server or tenant
  administration rights.
- **Core extensions for our pin**: DuckDB has not published binaries for a dev pin, so we build its
  core extensions and serve them from a signed channel (spec 0001). That CI must publish names
  DuckDB owns, such as `httpfs`; nobody else may.
- **An organisation** running kista wants its internal teams to publish their extensions, each team
  only its own names.
- **Enterest's shared tenant** hosts external publishers from many GitHub organisations. A publisher
  must not publish under a name it was not given, shadow DuckDB's names, or publish a file that is
  not what it claims to be.
- **The console and the node agent** read the index and need to tell published from mirrored, and
  shadowing from ordinary releases.
- `release add` trusts its operator: the footer has no name, so a binary built as `y` and added as
  `x` is served under `x` and fails only at `LOAD`, when DuckDB looks for `x`'s entry point.
- A yanked body can come back in another channel or slot. A known-bad artifact needs a tenant-wide
  ban.

## Design

### Verbs and grants

Grants (spec 0006) gain two verbs:

- `publish`: upload a Build of an extension into a channel;
- `promote`: release, in a channel, a Build that is in another channel of the tenant.

A grant's resource is the tenant, a channel, or an extension (in every channel or in one), as for
`install`. These two verbs are never implied by `admin`: publishing native code is granted
explicitly, so an administrator's long-lived install token cannot publish (spec 0007 left this to
this spec). An issuer-wide grant (`issuer:<record>`) cannot carry them, as it cannot carry `admin`.

- **Publishing** name `n` into channel `c` needs `publish` covering (`c`, `n`).
- **Promoting** name `n` from channel `s` to channel `t` needs `promote` covering (`t`, `n`) and
  `publish` covering (`s`, `n`): whoever promotes could have published the Build where it came from.
- Both channels are `signed` channels of the path's tenant.
- A tenant token used to publish, promote or block is held to spec 0007's management rules: issued
  within `auth.admin_token_max_age`, naming its writer.

### Reserved names

kista carries the names DuckDB owns, in `internal/reserved`, generated by `make reserved`:

- **core**, from the pin (`e2e/DUCKDB_PIN`): `internal_extensions[]`
  (`src/main/extension/extension_helper.cpp:66`), `AUTOLOADABLE_EXTENSIONS` and every extension
  named in the entry tables of `src/include/duckdb/main/extension_entries.hpp`, the directories of
  `extension/`, and the `duckdb_extension_load(...)` names of `.github/config/*.cmake`;
- **community**: the `extension.name` of every `extensions/*/description.yml` in
  `duckdb/community-extensions` at a pinned commit, and the directory names;
- **extra**: a short curated list in the repository, for names known from other DuckDB versions.

The generator only adds: a name that was ever reserved stays reserved, since clients may have
installed it. CI regenerates from the pinned checkouts and fails on a diff. (The alias names, such
as `http` or `sqlite`, are already refused by the name grammar of spec 0006.)

For `publish` and `promote`, a reserved name is covered only by grants that **name** it (other verbs
are not affected: a tenant administrator still manages `httpfs`'s releases): for publishing,
`publish` on that extension (in the channel or in every channel); for promoting, `promote` on it in
the target and `publish` on it in the source. A tenant- or channel-wide grant never reaches a
reserved name. A server administrator over the API and the CLI's operator are not limited. A release
under a reserved name is shown as `shadows: core | community`, computed when the index is read (so
it follows the list). Releases that exist when a name becomes reserved stay as they are.

### What a file must be

An uploaded file is what DuckDB's build writes (spec 0002): the binary, the 22-byte metadata prefix
(`00 93 04 10 "duckdb_signature" 80 04`), the 256-byte metadata and 256 bytes for a signature. On
the spooled body, before anything is committed, the server:

1. **parses the footer** with spec 0002's grammars; the declared `version` and `platform` must equal
   the footer's (a CI job that picked the wrong artifact fails instead of publishing it);
2. **requires the metadata prefix** right before the metadata. kista never rewrites a body it signs;
3. **checks the binary's format** against the footer's platform: `linux_*` is an ELF shared object
   (`ET_DYN`), `osx_*` a thin Mach-O dylib or bundle, `windows_*` a PE DLL; the machine is the
   platform's (`amd64`: x86-64, `arm64`: AArch64). `wasm_*` and unknown platforms are refused (wasm
   signatures are a follow-up). musl and glibc builds cannot be told apart and are not;
4. **checks the entry points**: DuckDB loads `<name>` by looking up one symbol
   (`src/main/extension/extension_load.cpp:805-860`, with `UsesCAPIV2` at lines 29-37 and
   `src/main/extension.cpp:141-148`):

   - `CPP` (or an empty ABI field): `<name>_duckdb_cpp_init`;
   - `C_STRUCT_UNSTABLE`, or `C_STRUCT` whose C API version parses as `vX.Y.Z` with `X` = 2:
     `<name>_init_c_api_v2`;
   - any other `C_STRUCT`: `<name>_init_c_api`.

   The binary must export that symbol strictly (below), and no other name ending in
   `_duckdb_cpp_init`, `_init_c_api` or `_init_c_api_v2` in any form the loader resolves (a file
   that is two extensions at once is refused). The files are read as the loaders read them:

   - **ELF**: the dynamic array where `PT_DYNAMIC`'s address is mapped (loadable segments sorted and
     not overlapping); `DT_SYMTAB` with `DT_SYMENT` 24, as many symbols as `DT_HASH` or
     `DT_GNU_HASH` reach (the `SHT_DYNSYM` section must agree and cover them; compressed sections
     are refused), names within `DT_STRSZ`. A strict export is a defined `STT_FUNC` symbol,
     `STB_GLOBAL` or `STB_WEAK`, visibility default or protected; every other non-local symbol
     counts against;
   - **Mach-O**: one source of exports only (the export trie of `LC_DYLD_EXPORTS_TRIE` or
     `LC_DYLD_INFO(_ONLY)`, or else `LC_SYMTAB` with `LC_DYSYMTAB`; two are refused), names with the
     `_` prefix. A strict export is a trie entry or an external, non-private section symbol; a
     re-export (another library's code) counts against;
   - **PE**: the export directory (data directory 0); each name read only within the section that
     holds it. A strict export is a name that is not a forwarder; a forwarder counts against.

   The readers are kista's own, bounded and read-only: every offset and count is checked against the
   file and its sections, the Mach-O trie walk keeps a visited set and a depth limit, all the names
   one parse reads are at most 128 MiB, the PE export names at most 65,536, and a parse runs under
   `recover` with a time budget. A file they cannot read is refused;
5. ignores the trailing 256 bytes (a signature an upload carries is replaced by the channel's).

This check makes what is served under a name load as that name. It is not a sandbox: a publisher
granted a name controls the code behind it.

`builds.checked` records that a Build passed checks 2-4; it is set once and never cleared. `kista
admin release add` runs the checks too, with `-unchecked` to skip 2-4 for a body the operator
vouches for (a test fixture, a platform kista cannot parse). An unchecked Build cannot be promoted
over the API (`409`); publishing the same body with the checks marks it checked.

### Publication and promotion routes (phase 1)

```text
POST /api/v1/tenants/{t}/channels/{c}/extensions/{ext}/releases
     ?version=&platform=[&visibility=public|private][&current=true|false]
     Content-Type: application/octet-stream; Content-Length required; the body is the file
POST /api/v1/tenants/{t}/channels/{c}/extensions/{ext}/releases/promote
     {"from_channel": "staging", "release": "<id>"}            one release, or
     {"from_channel": "staging", "version": "1.2.0"}           every active release of the version
     optional: "visibility": "private", "current": false
GET  /api/v1/tenants/{t}/channels/{c}/extensions/{ext}/releases[/{id}]     (spec 0007, widened)
```

- **Who** is decided from the path before the body is read (spec 0007): `publish`, or for promotion
  `promote`, covering (`c`, `ext`) with the reserved rule; for promotion, once the JSON body names
  the source channel, `publish` covering (source, `ext`), and a caller without it gets the same
  `404` as for a missing release. A `100-continue` client gets its `401`/`404` before sending the
  file.
- **Reading releases**: spec 0007's `GET …/extensions/{ext}/releases[/{id}]` is also open to holders
  of `publish` or `promote` covering (`c`, `ext`), so CI and release managers can find what to
  promote. They see the same shape without `created_by`/`state_changed_by`.
- **Publishing** is spec 0006's release add with the checks: the slot rules (a released version is
  immutable; the same body in the same slot with the same choices is the existing release, `200`;
  other choices or another body `409`), the channel must serve a `cpp` or `c_struct_unstable`
  build's DuckDB version (`400`), signing with the channel's active key outside transactions. It
  answers `201` with the release and `Location: …/extensions/{ext}/releases/{id}`.
- **Defaults**: `visibility` defaults to `private`, so a forgotten parameter never publishes a
  private extension to everyone; `current` defaults to `true` (spec 0006's default).
- **Promotion** releases the same Builds in `c`; nothing is copied. The source releases must be
  `active` (a deprecated or yanked one is not promoted), checked, and not blocked. Visibility is the
  source's unless the body asks for `private` (promotion never makes a private Build public; that is
  `release public` by the extension's administrator). For a version, every active release of (`ext`,
  `version`) in the source is promoted: every platform, every slot. The target must serve each `cpp`
  and `c_struct_unstable` build's DuckDB version, and some DuckDB version whose C API maximum
  accepts each `c_struct` build (spec 0006); otherwise `400` naming the platform and version. All
  signatures are made first, then one transaction under the target channel's lock inserts every
  release or none (a slot conflict on any is `409` for all). It answers `201` (or `200` when the
  target already holds them all with the same choices): a promotion of one release by id answers
  that release with its `Location`, a promotion of a version the list of releases.
- **Answers never tell** whether a body was already stored in this tenant or the storage domain: the
  whole body is always received, hashed and committed (spec 0005 writes it whether or not the hash
  exists), and a client's declared hash is never trusted. A `409` names the slot, not another
  release's id, for a caller who is not the extension's administrator.
- **Errors**: footer, prefix, format or entry-point mismatch: `400`, naming the check ("the binary
  does not export loadable_ext_init_c_api"); an unknown query parameter `400`; no `Content-Length`
  `411`; a length over `blob.max_body` plus the 256-byte signature `413` before reading; another
  media type `415`; an upload that ends before its length `400`, or is too slow `408`; a blocked
  body `409` ("blocked"); a channel without an active key `409`.

### Uploads

The publication route is the API's one raw-body route: spec 0007's JSON-only, 64 KiB rule does not
apply to it, and its limits are its own.

- `Content-Length` is required and at most `blob.max_body` plus the signature.
- The body is read at no less than `serve.min_rate` (a reader that moves the connection's read
  deadline forward as bytes arrive, the counterpart of the response writer's, and clears it when the
  body ends), and within an absolute deadline of `Content-Length / min_rate` plus a minute.
- Concurrency, checked after the decision and before reading: at most `publish.max_per_principal`
  uploads per principal (default 2), `publish.max_per_tenant` per tenant (default 8), and one fewer
  than `blob.max_ingests` on the server (the CLI and intake keep a slot); then the blob service's
  ingest semaphore is tried without waiting. Over a limit: `429` with `Retry-After` (CI should
  retry). The counters are per replica.

```yaml
publish:                         # file-only
  max_per_principal: 2
  max_per_tenant: 8
  providers:                     # phase 1b: trusted-publishing issuers; default: GitHub Actions
    - name: github
      url: https://token.actions.githubusercontent.com
```

### Block (phase 1)

```text
blocks   tenant_id, body_hash, reason, created_at, created_by      pk (tenant_id, body_hash)

GET    /api/v1/tenants/{t}/blocks                       tenant admin
POST   /api/v1/tenants/{t}/blocks {body_hash, reason}    tenant admin; 201, Location
GET    /api/v1/tenants/{t}/blocks/{body_hash}           tenant admin
DELETE /api/v1/tenants/{t}/blocks/{body_hash}           tenant admin; 204
```

- **Order**: the block row is committed first. Then every signed channel of the tenant is visited
  under its channel lock, and each release of a Build with that body is yanked (`state_changed_by`
  is the blocking actor; the reason stays on the block row), bumping the channel's
  `release_version`. Publishing, promoting and `release add` check `blocks` before committing the
  body and again inside the insert transaction, under the channel lock; so a release either commits
  before the sweep reaches its channel (and is yanked by it) or sees the block.
- A hash the tenant does not hold may be blocked (a known-bad artifact, ahead of time); the answer
  is the same. Blocking a hash already blocked sweeps again (finishing a sweep that failed half-way)
  and answers `200` with its `Location`. A tenant holds at most 10,000 blocks.
- Removing a block lets the body be released again; yanked releases stay yanked (a fix is a new
  version, spec 0006).
- The index shows `blocked: true` on a yanked row whose body is blocked, so the node agent and the
  console can tell it from an ordinary yank. The blocked hashes are part of each channel's snapshot
  (spec 0007): a block and an unblock bump `release_version` on every signed channel of the tenant.
- A block stops a known artifact, not a publisher: one changed byte is a new body. Stopping a
  publisher is removing its grants or the publisher.
- Spec 0009's intake checks `blocks` the same way. This replaces spec 0006's follow-up "blocks join
  resolution".
- CLI: `kista admin block add <tenant> <hash> -reason …`, `block list`, `block remove`.

### Publishers

A **publisher** is a named identity in a tenant that may only publish and promote. Grants name it as
`publisher:<name>`; its credentials authenticate it. Credentials change (a binding gains an
environment, a key is rotated) without touching its grants.

```text
publishers            id, tenant_id, name, created_at, created_by        unique (tenant_id, name)
publisher_github      id, publisher_id, provider, owner_id, repository_id, workflow,
                      ref null, environment null, created_at, created_by
api_keys (phase 2)    id, publisher_id, prefix, hash, expires_at, created_at, created_by,
                      last_used_at null                                  unique (hash)
```

**Trusted publishing (GitHub Actions, phase 1).** A GitHub credential binds:

- `owner_id` and `repository_id`: GitHub's `repository_owner_id` and `repository_id` claims, digit
  strings, never names (a renamed or re-created repository does not inherit the binding);
- `workflow` (required): the `workflow_ref` claim without its `@<ref>`, for example
  `hugr-lab/duckdb-acl/.github/workflows/release.yml`; the calling workflow is matched, and a
  reusable workflow it calls runs under the caller's identity;
- `ref` (optional): a pattern over the `ref` claim, such as `refs/tags/v*` (`*` matches within a
  segment, `**` across);
- `environment` (optional, recommended for credentials whose publisher holds `promote` or publishes
  outside `staging`): the `environment` claim exactly, so GitHub's environment protection rules
  (required reviewers, branch and tag rules) gate the job.

A token whose `iss` equals a configured provider URL exactly is verified against that provider only
(discovery and JWKS through egress, with a verifier and cache of its own and the same refresh limits
as spec 0006's): `aud` must be the tenant's canonical audience (`<public_url>/<tenant>`, which the
workflow requests with `id-token: write`), never an assigned one; its lifetime at most an hour and
`iat` within `admin_token_max_age`; `event_name` must not be `pull_request`, `pull_request_target`
or `workflow_run` (they run code a contributor controls with the base repository's identity). The
path tenant's GitHub credentials whose fields all match make their publishers the caller's
principals. A tenant issuer record cannot have a provider's URL: adding one is refused, and an
existing one is disabled with a log line at startup (never a startup failure).

**API keys (phase 2).** A key is `kista_<prefix>_<secret>`: `prefix` is 8 random hex characters
(shown in lists, never used for lookup), `secret` 32 random bytes in base32. Only the SHA-256 of the
whole key is stored (the secret is random, so a slow hash adds nothing; lookup by that hash has no
timing to learn from). `expires_at` is required, at most a year; a publisher may hold several keys,
so a new one is issued before the old one is removed. A Bearer starting with `kista_` is looked up
only on the routes publishers use; the key's tenant must be the path's (otherwise `401`).
`last_used_at` is updated at most once an hour. Elsewhere a `kista_` Bearer is never looked up: the
API answers `401` (not a valid token), the DuckDB routes treat it as no token (spec 0006).

**What publishers may do**, whatever their grants say: publish, promote, read the releases their
grants cover (above), and `GET …/whoami` (their publisher, the matched credential, their grants).
Nothing else: no install, no management, no index beyond the public view. A grant to a publisher may
carry only `publish` and `promote` (others are refused when added, and ignored when evaluated).

**Management** (tenant admin): `GET, POST /api/v1/tenants/{t}/publishers`, `GET, DELETE
…/publishers/{name}`; `GET, POST …/publishers/{name}/github`, `DELETE …/github/{id}`; phase 2: `GET,
POST …/publishers/{name}/keys` (the key appears only in the `POST` answer), `DELETE …/keys/{id}`.
Removing a publisher removes its credentials and grants and bumps the tenant's `auth_version`, so
caches drop it at the next request. CLI: `kista admin publisher add|list|remove`, `publisher github
add|remove`, `publisher key add|remove` (phase 2).

**Principals and actors**: a publisher principal is `publisher:<name>`; grants reference the
publisher by id (`grants.publisher_id`), so a publisher re-created under the same name starts with
no grants. Actors are recorded as `publisher:<tenant>/<name>` with the credential (`github:<id>` or
`key:<prefix>`). The prefixes `publisher:` and `kista_` cannot collide with spec 0006's principals,
which always name an issuer record.

### Provenance and the index

- `releases` gains `origin` (`admin` | `publication` | `promotion`; later `upstream`) and
  `provenance` (text, at most 4,000 bytes, JSON): the actor and, for trusted publishing, the
  provider, owner and repository ids and names, workflow, ref, commit sha, run id and attempt; for
  promotion, the source channel and release. A Build may be released many times, so provenance
  belongs to the release; the Build keeps its first origin.
- Index rows (spec 0007) gain `origin`, `shadows` and `blocked` for every caller who sees the row;
  `provenance` for the extension's administrators and holders of `publish` or `promote` covering it.
  Who made a release (`provenance.actor`, like `created_by`) is shown to the extension's
  administrators, with server and OS identities masked as spec 0007's `created_by: server`, and not
  to its publishers.

### Data model

Migration 0005 (phase 1a, `min_reader 5`: an older binary would ignore blocks), on PostgreSQL, SQL
Server and SQLite:

```text
builds             + checked (boolean | bit | INTEGER), default false
releases           + origin varchar(16) not null default 'admin', provenance varchar(4000) null
blocks             tenant_id, body_hash varchar(64), reason varchar(400), created_at, created_by
```

Grant verbs gain `publish` and `promote` in phase 1a too (verbs are a checked text column: no schema
change).

Migration 0006 (phase 1b):

```text
publishers, publisher_github                                   (as above)
grants             issuer_id becomes nullable; + publisher_id null, fk -> publishers (cascade);
                   check: exactly one of issuer_id and publisher_id; kind gains 'publisher'
```

Making `grants.issuer_id` nullable rebuilds the table on SQLite and, on SQL Server, drops and
recreates the foreign key, the check and the index by looking up their generated names. Grant reads
become `LEFT JOIN`s with nullable scans; the duplicate check compares with `COALESCE`. Phase 2 adds
`api_keys`.

### Package layout

```text
internal/extfile    + the metadata-prefix check (the prefix is 22 bytes)
internal/symbols    format and entry-point checks: bounded ELF, Mach-O and PE readers
internal/reserved   generated name lists; make reserved
internal/release    + publish (checks, provenance), promote, block
internal/auth       + provider tokens, publishers' principals; phase 2: API keys
internal/authz      + publish and promote; the reserved rule; publisher actors
internal/api        + the raw-body publication route, promote, blocks, publishers
internal/store      migration 0005
```

### Changes to earlier specs

- **0001**:
  - shadowing a reserved name needs grants that name it, not tenant `admin`;
  - a publisher may publish into any signed channel it has `publish` on, `staging` being the usual
    one, and a channel that takes direct publications must not share trusted keys with `prod`;
  - the init symbols are those of the pin (above; there is no `<name>_init`);
  - API keys are part of the open server, with trusted publishing.
- **0002**: the metadata prefix is 22 bytes, not 19 (also in `internal/extfile`'s comments).
- **0005**: storage garbage collection is not this spec's; it moves to a follow-up of its own.
- **0006**: `admin` implies every verb except `publish` and `promote`; blocks yank instead of
  joining resolution.
- **0007**: the publication route is the raw-body exception; the extension release reads are open to
  `publish`/`promote` holders.

## Security

- **Names bind to entry points**: what is served under a name exports exactly that name's entry
  point and no other extension's, so it loads as that name. The readers parse a spooled file with
  bounds, never execute it, and refuse what they cannot read. It is a naming check, not a code
  review.
- **Footers bind to requests**, and released versions stay immutable (spec 0006's slots).
- **Explicit verbs**: `publish` and `promote` are never implied by `admin` and never carried by an
  issuer-wide grant; people use fresh tokens for them.
- **Reserved names** need grants that name them for publishing and for both sides of a promotion.
- **Promotion is not a bypass**: it needs `publish` in the source, keeps or narrows visibility,
  takes only active, checked, unblocked releases.
- **Publishers are narrow**: they publish and promote only, with credentials bound to immutable ids,
  a workflow and optionally a ref and an environment; pull-request events are refused; audiences are
  canonical only. API keys are stored hashed, expire, are tenant-bound, and are never looked up
  outside the publishers' routes.
- **Block is race-free**: the block commits first and every release insert re-checks it under its
  channel lock.
- **No existence leaks**: the path decides first; answers do not depend on whether a body is stored;
  a promotion source the caller may not publish from answers like a missing one; conflicts do not
  name other releases to non-administrators.
- **Signing** is unchanged: the active key, outside transactions, verified after signing.
- **Resources**: uploads are bounded by length, read rate, an absolute deadline, concurrency per
  principal and tenant, and the ingest semaphore; parsers by file size, counts and time.

## Testing

- **Readers**: ELF, Mach-O and PE fixtures built byte by byte in the tests (no cross toolchain), and
  DuckDB's own builds at the pin (Mach-O on macOS, ELF on Linux, in the reader tests and the e2e
  suite): the right entry point; another name's; two extensions in one file; an undefined import of
  it; a hidden or local symbol; the wrong ABI's symbol; the wrong machine; an executable instead of
  a shared object; universal Mach-O; section headers that disagree with `PT_DYNAMIC`; compressed
  sections; truncated and cyclic inputs; a fuzz target per reader with a capped input size.
- **Footer and prefix**: declared vs footer values; a missing prefix; the C API v1/v2 rule.
- **Reserved names**: the generated lists against the pins (CI); tenant- and channel-wide grants do
  not reach `httpfs`; a named grant does; promotion needs naming on both sides; `shadows` in the
  index.
- **Routes**: every route × caller (spec 0007's matrix plus publishers, `publish` and `promote`
  holders on one extension and channel-wide, an administrator without the verbs); promotion without
  `publish` on the source, of a version across platforms (all or none), of a private, deprecated,
  unchecked or blocked release; re-publishing the same body (`200`) and with other choices (`409`);
  `411`, `413`, `415`, `429`; a slow upload cut by the read rate.
- **Block**: concurrent block and publish/promote never leave the body served; pre-emptive blocks;
  `blocked` in the index.
- **Trusted publishing**: a fake provider: wrong owner, repository, workflow, ref pattern,
  environment, audience (an assigned one), lifetime, event name; an issuer record with the
  provider's URL refused and disabled; a removed publisher's token refused at the next request.
- **Store**: migration 0005 on all three dialects, nullable issuer ids, grants of publishers.
- **e2e**: CI publishes `loadable_extension_demo` into `staging` through the API with a fake GitHub
  token; `INSTALL … FROM` and `LOAD` it; promote its version to `prod` and install from there;
  `demo_capi`, a reserved name, needs a grant naming it; block the body and see `INSTALL` fail;
  publishing the demo file under another name is refused by the entry-point check.
- **Phase 2**: API keys: expired, removed, of another tenant, used on the index, management or the
  DuckDB routes, two keys overlapping during a rotation.

## Alternatives considered

- **Trusting the footer and the declared name** (as `release add` did): the footer has no name; the
  entry point is the only name the binary carries.
- **Appending a missing metadata prefix**: kista would rewrite bodies it signs; refusing is simpler.
- **`admin` implying `publish`**: an administrator's install token (up to a week in a DuckDB secret)
  could then publish native code.
- **Trusted publishing on tenant issuer records** (GitHub as an issuer record, the owner id as a
  required claim, the repository id as a role): one organisation per tenant (issuer URLs are unique
  per tenant), and no way to keep such principals to publishing.
- **Bindings and keys as principals of their own**: rotating a key or editing a binding would drop
  its grants; a publisher holding credentials keeps them.
- **API keys for installs**: installs authenticate with short-lived tokens (tresor, spec 0006).
- **Promotion by copying the file**: a release is a Build plus the target's signature.
- **Block by joining resolution**: a yank is visible in the index and to the re-signer already.

## Follow-ups

- Spec 0009: upstream names join the reserved rule; adding an upstream that collides with a
  publication is refused until an administrator resolves it; intake checks blocks.
- Spec 0010: publication, promotion and block events.
- Storage garbage collection (blobs no Build references).
- wasm extensions (their signature is a custom section).
- Other CI providers (GitLab, Azure Pipelines, GitHub Enterprise Server) as more providers with
  their claim mappings.
- Enterest: the developer cabinet and cross-tenant publisher identity build on publishers.
