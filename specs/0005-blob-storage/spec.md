# Spec 0005: Blob storage for extension bodies

- **Status**: phases 1, 2, 3a and 3b implemented
- **Date**: 2026-10-07
- **Author**: vgsml, Claude

## Summary

Extension bodies are stored once, as content-addressed precompressed streams, in an object store
behind one interface. A blob service on top:

- **spools** an incoming file;
- lets the caller **verify** it: footer, upstream signature, init symbol;
- **commits** it: precompresses (spec 0002), uploads, and records the result;
- **serves** a channel's file from the stored stream plus that channel's signature, as gzip with
  `HEAD` and `Range`. Every byte is verified against chunk digests held in the database before it
  is sent.

Tenants belong to **storage domains**: named stores from config. Dedup happens inside a domain,
which is how data residency and sovereign clouds are kept apart (spec 0001).

Delivery is phased, like spec 0004:

1. the interface, the contract suite, `fs`, `s3` with static key files (MinIO, Cloudflare R2,
   S3-compatible stores), the service, and migration 0002;
2. `azureblob`, with spec 0004's Azure credentials;
3. with the AWS/GCP work: (3a) platform identity for `s3` on AWS (IRSA, Pod Identity, instance
   roles, through a hardened `internal/cloud/aws`), with spec 0004's phase 3; (3b) `gcs`, with its
   phase 4.

## Problem

Spec 0001 serves `body ‖ channel signature` without copying binaries per channel or per tenant.
Spec 0002 built the pieces:
- the composite body hash;
- a precompressed deflate stream ending with a sync flush;
- per-chunk stream digests;
- a gzip writer that verifies each chunk before sending it.

Nothing stores those streams yet. Every deployment keeps objects somewhere different, so the object
store is pluggable (the owner's rule: Azure is one option, everything cloud-specific behind an
interface).

## Design

### Objects and records

- **Object.** The precompressed stream of one body is stored under its own content address:
  `streams/<stream hash hex>`, where the stream hash is spec 0002's `StreamHash`. Objects are
  immutable in content. A write to an existing key writes the same bytes, so overwriting is always
  safe.
- **Record.** A database row holds what serving needs and the object store must not be trusted
  with:

```text
blobs            domain, body_hash, stream_hash, body_len, body_crc32, stream_len,
                 stream_chunks (32 bytes per MiB of stream), corrupt_at null, created_at,
                 committed_at (every commit sets it; a corruption mark applies only to the commit
                 its reader saw, so a stale reader cannot mark a repaired record)
                 pk (domain, body_hash); index (domain, stream_hash)
storage_domains  name pk, kind, store_id, created_at
                 -- store_id: a hash of the store's identity (kind, endpoint or account, bucket or
                 -- container or root, prefix), pinned at first use
deployment       one pk (always 1), id, created_at
                 -- the deployment's id, created on first use; the domain markers carry it
```

- **No raw body is stored.** Signing needs only the body hash, serving uses the stream, and the rare
  plain-name answer inflates it. This amends spec 0001, which planned to keep a raw copy too.
- **The footer belongs to the Build** (spec 0006), not to the blob.

**Migration 0002** (`-- +min_reader 1`, purely additive):

| Column | PostgreSQL | SQL Server | SQLite |
| --- | --- | --- | --- |
| hashes | `varchar(64)` hex | `nvarchar(64) BIN2` | `TEXT` |
| `body_crc32`, lengths | `bigint` | `bigint` | `INTEGER` |
| `stream_chunks` (up to about 33 KB at 1 GiB) | `bytea` | `varbinary(max)` | `BLOB` |

It also adds the single-row `deployment` table, and `tenants.storage_domain` as `varchar(16)` / `nvarchar(16) BIN2` / `TEXT`,
`NOT NULL DEFAULT 'default'`. On SQL Server the default constraint is named.

### The store interface

```go
type Store interface {
    // Put stores a complete object; it becomes visible only when complete, and replaces any
    // existing object with the key.
    Put(ctx context.Context, key string, r io.ReaderAt, size int64) error
    // Get reads n bytes from off (n < 0: to the end).
    Get(ctx context.Context, key string, off, n int64) (io.ReadCloser, error)
    Stat(ctx context.Context, key string) (size int64, err error)          // ErrNotFound
    Delete(ctx context.Context, key string) error                          // GC (spec 0016)
    List(ctx context.Context, prefix string, fn func(key string, size int64, modified time.Time) error) error
    // Anonymous reports whether key can be read without credentials, when the backend can tell.
    Anonymous(ctx context.Context, key string) (readable, ok bool)
    // ID identifies the store (kind, endpoint or account, bucket or root, prefix) for pinning.
    ID() string
}
```

- **Keys** are generated by kista: `streams/<64 lowercase hex>`, `tmp/<uuid>`, and
  `kista-domain.json` (the marker). They are validated against exactly this grammar on every call,
  with no upper case, no `..`, no other prefixes. `List` accepts only `streams/` and `tmp/`.
  Configured prefixes are validated the same way.
- **Bounded calls.** Every remote call has a timeout on connecting, on time to response headers,
  and on idle time: a connection that makes no progress in either direction for `timeout` fails.
  Progress in one direction keeps the other alive (a slow upload is not cut while the server has not
  answered yet), and a pooled connection is closed after `timeout/2` idle.
  `Stat` and `Delete` are also bounded as a whole. There are at most 3 attempts, counting the SDK's
  own retries. Clients ignore proxy environment variables and do not follow redirects. `fs` is
  local and takes no timeout.
- **Errors** keep the backend's status, an error code of the expected shape, and a request id, never
  bodies, keys, URLs or principals. The SDKs' own error strings, which include the URL and body, are
  never wrapped.

### Backends

**`fs`: a local directory** (phase 1). It also covers a Kubernetes persistent volume.
- All access goes through `os.Root`, so no path and no symlink can leave the root.
- `Put` writes `tmp/<uuid>` (`O_EXCL`, mode `0600`) and fsyncs it, renames it into place, then
  fsyncs the directory. The rename replaces the old object atomically. Directories are created with
  mode `0700`.
- A shared `ReadWriteMany` volume makes every pod a writer of every object. That is documented.

**`s3`: S3-compatible stores** (phase 1; `github.com/minio/minio-go/v7`, Apache-2.0).
- **Config:**
  - `endpoint`: an `https://host[:port]` URL; `http://` only on loopback with `profile: dev`;
  - `bucket` and `prefix`;
  - `region`, required (no `GetBucketLocation` lookup; R2 uses `auto`; jurisdiction endpoints such
    as `<acct>.eu.r2.cloudflarestorage.com` for residency);
  - `lookup: path|dns`;
  - `sse: none|s3|kms`, required: R2 and MinIO without KMS take `none`, AWS takes `s3` or `kms`,
    with `kms_key_id` for `kms`.
- **Credentials in phase 1:** static access-key and secret files (`access_key_file`,
  `secret_key_file`, mode `0600` or narrower, re-read on every signing so rotated files are picked
  up), wrapped in kista's own `credentials.Provider`. minio-go's IAM,
  chain, environment and file providers are never used: they read `AWS_*`, `MINIO_*`,
  `~/.aws/credentials` and container-credential URLs from the environment.
- **Platform identity on AWS** (phase 3a, with spec 0004's `awskms`):
  - Instead of the key files, an `s3` domain may name `identity: { kind: pod_identity | irsa |
    imds | ecs }` (with `identity.role_arn` for `irsa`), an optional `role_arn` to assume after it,
    and `account`.
  - Its credentials come from `internal/cloud/aws`, exactly as an `awskms` source's do, in the
    domain's `region`.
  - kista's provider hands them to minio-go with the session token and the expiry. It reports
    itself expired at every request, and serves from the SDK's cache, which refreshes ahead of
    expiry. A retrieval has its own bounded deadline.
  - Exactly one of the key files and `identity` is set.
- **Identity goes only to AWS S3.**
  - The endpoint is `https://` with no port. Its host, lowercased, is one of these, where
    `<region>` is the domain's `region`:
    - `s3.<region>`, `s3.dualstack.<region>`, `s3-fips.<region>` or `s3-fips.dualstack.<region>`,
      followed by `.amazonaws.com`;
    - `s3.<region>` or `s3.dualstack.<region>`, followed by `.amazonaws.com.cn`.
  - So platform identity for `s3` is on `aws`, `aws-us-gov` and `aws-cn` only. The legacy global
    forms, PrivateLink endpoints and the ISO and EUSC partitions are not accepted yet.
  - `ca_file` is refused with `identity`: AWS endpoints are verified against the system roots.
  - Every request carries `x-amz-expected-bucket-owner: <account>`, set by kista's transport. S3
    then refuses a bucket that another account owns, for example one deleted and re-created by
    someone else, so private extensions are never written into it.
    - S3 requires every `x-amz-*` header to be signed, and minio-go has no option for a header on
      every request. So the transport adds it and signs the request again (SigV4, the same
      credentials, payload hash and time).
    - A request it cannot sign so (streamed or trailer payloads, which minio-go uses only over
      http) is refused, never sent unsigned.
  - The same transport refuses a request to any host but the configured endpoint or its
    virtual-hosted form. minio-go rebuilds AWS hosts from its own region map, and turns dual-stack
    on for every AWS endpoint; kista turns that off unless the endpoint is a `dualstack` one.
  - With an `s3-fips.` endpoint, STS is reached at its FIPS endpoint too.
- **Put:** a single PUT, or a multipart upload from the spool file (`ReadAt`, no buffering), aborted
  on every error; kista aborts it itself with a fresh deadline, since minio-go's own abort uses the
  call's context and sends nothing once that is cancelled.
- **Get:** one ranged GET (`minio.Core`, no `HEAD` first, no `If-Match` pinning to an ETag that a
  concurrent re-upload changes). Errors from reading the body are described like every other.
- **TLS:** the system roots, or only `ca_file` for an internal CA. A bucket name with dots cannot be
  used with `lookup: dns` over https (the certificate does not match), so config refuses it. Documentation adds an `AbortIncompleteMultipartUpload` lifecycle rule.
  `MaxRetry` is capped.
- Least privilege: `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject` and `s3:ListBucket` on the
  prefix, plus `kms:GenerateDataKey` and `kms:Decrypt` for SSE-KMS.

**`azureblob`: Azure Blob Storage** (phase 2; `azblob`, with `internal/cloud/azure` credentials).
- Config: `account`, `container`, `cloud` (the blob host is derived from it), `prefix` and
  `identity`.
- The blob host is `<account>.blob.core.windows.net`, `.blob.core.chinacloudapi.cn` or
  `.blob.core.usgovcloudapi.net`; the token comes from spec 0004's credential (managed or workload
  identity, `default` only in dev), and is never sent over http.
- `Put` of an object up to 16 MiB is one Put Blob. A larger one stages 16 MiB blocks whose ids are
  derived from the key (for a stream, its hash) and the block index, then commits the block list.
  Two replicas writing one key stage identical blocks, so neither commit invalidates the other.
  The blocks of a failed upload are never visible; Azure discards uncommitted blocks after a week.
- At most 3 attempts per call and no per-try time limit (azcore's would also cut a long download);
  the shared transport bounds connecting, headers and idle reads and writes, as for `s3`.
- The anonymous check is an unsigned `HEAD` of the marker: `200`, and `404 BlobNotFound` (anonymous
  reads reach the container, the key is just missing), are public; `404 ResourceNotFound`, `401`,
  `403` and `409` (public access forbidden on the account) are private.
- A ranged download whose `Content-Range` does not start at the requested offset is refused. A
  `Retry-After` up to 10s is honoured (azcore does not retry a longer one at all).
- The Entra token requests (and Key Vault's, spec 0004) use a client without proxies from the
  environment, so `HTTP_PROXY` cannot route the managed-identity request and its token elsewhere.
- SAS tokens and connection strings are refused (config has no field for them, and an endpoint with
  a query is refused). A shared key (`account_key_file`, mode `0600`) and an `endpoint` override are
  allowed only together, only with `profile: dev`, on loopback, for the Azurite emulator.
- Least privilege: Storage Blob Data Contributor on the container. The documentation says to set
  `allowBlobPublicAccess = false`.

**`gcs`: Google Cloud Storage** (phase 3b, with spec 0004's `gcpkms`). It uses the JSON API over
REST, with no Google SDK.
- **Config:** `bucket`, `prefix`, `principal`, `credentials_file` and `endpoint_url`. The last
  three work as `gcpkms`'s do:
  - credentials from the metadata server when the file is absent, an `external_account` file, or
    a `service_account` key file in dev only;
  - `endpoint_url` only in dev, on loopback, without a credentials file: `fake-gcs-server` in the
    tests.
- **The host** is `https://storage.googleapis.com` only (REP endpoints are not supported yet). The
  credentials come from spec 0004's `internal/cloud/gcp`.
- **Object names** in `/o/<name>` are escaped with `/` as `%2F`.
- **Put:**
  - An object up to 16 MiB is one multipart upload (`uploadType=multipart`): the object resource
    with its CRC32C, then the bytes. A media upload is not used, because the JSON API ignores
    `x-goog-hash` there (found live, 2026-10-14: a wrong hash was stored with `200`).
  - A larger one is a resumable upload:
    - It is started with `X-Upload-Content-Length` and the CRC32C in the object resource.
    - Its session URI must be on the store's endpoint, on the `/upload/storage/v1/b/<bucket>/o`
      path, before any byte is sent to it. The URI is a bearer capability and is never logged.
    - Chunks of 16 MiB are read from the spool file (`ReadAt`). A `308` continues from its `Range`
      header, which may acknowledge fewer bytes than were sent.
    - A failed chunk is followed by a backoff (honouring `Retry-After`) and a status query
      (`Content-Range: bytes */<total>`) before it is sent again. A 4xx other than 408 and 429
      ends the upload at once. Each chunk has three failures, and the whole upload a bounded
      number of rounds.
    - A failed upload is cancelled with a fresh deadline (`DELETE`; `499` is success).
  - Either kind becomes visible only when complete. The final answer's `crc32c` and `size` must
    match kista's. Otherwise that generation is deleted (`ifGenerationMatch`), so a later writer's
    object is not, and the Put fails. GCS itself refuses bytes whose CRC32C differs from the
    object resource's (`400`), for multipart and resumable uploads alike; fake-gcs-server does not
    emulate it, and the live tests prove it.
- **Get:**
  - Offset 0 with no length sends no `Range` and wants `200`. Otherwise a `Range`, and a `206`
    whose `Content-Range` starts at the offset.
  - `Accept-Encoding: identity`: kista sets no `Content-Encoding`, so GCS never transcodes.
- **Stat, Delete, List:**
  - `size` is a decimal string.
  - `List` pages by `pageToken`, and refuses a page token repeated.
  - A `404` is `ErrNotFound`.
- **Anonymous check:** an unauthenticated `GET` of the marker's metadata.
  - `200`, or `404` for a missing object (or bucket), means public, and kista refuses the domain.
  - `401` and `403` mean private.
  - Anything else is an error.
  - The check covers the bucket only under uniform bucket-level access, which the documentation
    requires.
- **Errors** keep the HTTP status and the first error's `reason` word (`notFound`, `forbidden`).
  At most 3 attempts on `429` and `5xx`, honouring a `Retry-After` up to 10 s.
- **Incomplete uploads:** a resumable session GCS never completed expires on its own after a week,
  and holds no object, so the collector has nothing to abort.
- **Least privilege:** `roles/storage.objectUser` on the bucket (create, get, delete and list
  objects). The bucket uses uniform bucket-level access and public access prevention. Soft delete
  and versioning keep deleted objects, at a cost.
- **Tests:**
  - The contract suite runs against `fake-gcs-server` (`fsouza/fake-gcs-server`, BSD-2-Clause, pinned
    by digest), as a `docker run` step gated by `KISTA_TEST_GCS`.
  - An `httptest` fake covers what fake-gcs-server does not emulate: a short `308`, the status
    query after a failed chunk, `429` with `Retry-After`, the cancel, the CRC32C check, the
    escaped names and multi-page lists.

### Storage domains

```yaml
blob:                               # file-only, like signers
  domains:
    - name: default
      kind: s3
      s3: { endpoint: "https://minio.internal:9000", bucket: kista, region: us-east-1, lookup: path,
            sse: none, access_key_file: /run/secrets/s3-access, secret_key_file: /run/secrets/s3-secret }
    - name: cn
      kind: azureblob
      azureblob: { account: kistacn, container: bodies, cloud: china,
                   identity: { kind: workload, client_id: "…", tenant_id: "…" } }
  spool_dir: /var/lib/kista/spool   # the default; in dev with SQLite, beside the database file
  max_body: 1GiB                    # the default; at most 4GiB
  max_ingests: 4                    # concurrent spools; disk use is about max_ingests × 2 × max_body
```

A remote domain also takes `timeout` (connect, headers and idle reads or writes; default 30s, 1s..5m).

- **`default` is required.** Configured domains must include `default`: tenants created without
  `-domain`, and every tenant that existed before migration 0002, live there.
- **Default.** Without a `blob` block, kista uses one `fs` domain, `default`, under
  `/var/lib/kista/blobs` (in dev, a directory beside the SQLite file). kista needs nothing but
  DuckDB.
- **Pinned.** At startup every configured domain's `store_id` is compared with
  `storage_domains` (and pinned on first use). A domain that now points at another store refuses to start. Two domains whose
  stores overlap (same kind and bucket, container or root, with one prefix containing the other) are
  refused at config validation and again by store identity at startup. A store's identity is
  normalized (the endpoint lowercased and without its default port; an `fs` root with symlinks
  resolved); two different host names for one bucket are not detected, and the marker is what
  catches them.
- **Order.** Existing pins are compared first; then every store's marker is checked (written if
  absent) and the public check runs; only then are new domains pinned. A store kista refused is
  never pinned, so pointing config at another store is enough to recover.
- **Marker.** Each domain's store holds `kista-domain.json`: the domain name, the store id, and the
  deployment's id (kept in the database). A store whose marker names another deployment or domain is
  refused. After writing a marker kista reads it back, so of two deployments that claim one empty
  store at the same moment, the one whose marker was overwritten refuses to start. Two kista deployments never share a prefix, so one's garbage collection cannot delete the
  other's objects.
- **Not public.** At startup kista makes an anonymous, unsigned `HEAD` of the marker. If that
  succeeds, the domain is public, and kista refuses to start. The same check (`CheckPublic`) runs
  periodically once kista serves (spec 0006). A backend that cannot tell is logged, not refused.
  Only the marker is probed: a policy that makes just `streams/` public is not detected, which the
  deployment documentation covers. `kista admin blob check` runs all of these checks and lists
  tenants whose domain is not configured.
- **Tenants.**
  - A tenant's domain is set at creation (`kista admin tenant create … -domain cn`), validated
    against the loaded config, and never changes in this spec.
  - At startup, every tenant's domain must exist in config. A tenant whose domain is missing is
    served nothing; its requests fail closed, and the condition is logged. It never falls back to
    another domain.

### Spool, verify, commit

```go
sp, err := svc.Spool(ctx, domain, r)   // the whole file, at most max_body + 256 bytes
// sp.File() *extfile.File: metadata, body hash, signature (spec 0002 extfile.Open over the spool)
// the caller verifies: the footer against the declared name/version/platform, the upstream
// signature (spec 0009), the init symbol (spec 0008)
rec, err := sp.Commit(ctx)             // stores the body
sp.Close()                             // always; removes the spool files; idempotent after Commit
```

- **Spool.**
  - `spool_dir` is a directory kista creates with mode `0700` and checks it owns.
  - Files are created with `O_EXCL` under random names, mode `0600`.
  - At most `max_ingests` spools exist at once; a semaphore limits them, and the size cap applies
    while reading.
  - Leftover spool files are swept at startup: those untouched for an hour, since another process
    (`kista serve`, `kista admin release add`) may be spooling into the same directory.
  - The spool is read through one open descriptor, never reopened by path, so what the caller
    verified is what is stored.
- **Commit:**
  1. precompress the spooled body (spec 0002 `Precompress`), asserting the result's body hash equals
     the spool's;
  2. claim the stream (spec 0016: under the stream's lock, waiting while the collector deletes it);
  3. upload the stream to `streams/<stream hash>`, **always**, replacing any existing object;
  4. insert the record, under the stream's lock, if the claim is still live (otherwise claim and
     upload again). If it exists (a dedup hit), keep the first record when its stream is still the
     uploaded one, otherwise update it to the new stream (the replaced one is marked for the
     collector), and clear `corrupt_at`.
- **Why always upload:**
  - the same work and timing whether or not another tenant in the domain already stored the body, so
    an upload reveals nothing (spec 0001);
  - an object that is missing, planted or bit-rotted is repaired by the next commit of that body.

  The cost is a repeated upload per ingest of an already-stored body. An optimization for public
  upstream bodies is a follow-up.

### Serving

`svc.OpenGzip(ctx, rec, sig)` and `svc.OpenPlain(ctx, rec, sig)` take a **record that the caller
has already resolved through a Build it is authorized to see** (specs 0006 and 0008). There is no
lookup by a raw hash from a request.

Each returns a `File`:
- `Size`;
- `ETag`: `H("gz" ‖ stream hash ‖ body hash ‖ signature)` or `H("plain" ‖ body hash ‖ signature)`.
  The gzip bytes change when a re-commit makes another stream (another compressor version), so the
  gzip ETag includes the stream hash: httpfs compares ETags between its ranged requests and must
  never splice two streams. This amends spec 0001;
- `ContentType`: `application/gzip` or `application/octet-stream`, set so that `ServeContent` never
  sniffs and a `HEAD` reads nothing;
- `NewReader(ctx) io.ReadSeeker`, per request.

**Gzip.** The file is the gzip header, the stored stream, a final stored block with the 256
signature bytes, and the trailer. Total size: `stream_len + 279`; chunk boundaries sit at
`10 + k × 1 MiB`.
- A read fetches one ranged `Get` from the first chunk it needs to the end of the stream; the reader
  is closed when the response ends, which cancels the rest (`ServeContent` does not tell a reader
  where a range ends).
- It verifies each chunk against the record as it streams, and copies out only verified bytes. The
  last, partial chunk is checked at its exact length.
- A non-sequential read reopens the range.
- The header, the tail and the trailer are built in memory.

**Plain.** The plain name is fetched only through httpfs (spec 0002). It is served by inflating the
verified stream and appending the signature.
- No `Accept-Ranges` is sent and the file is sent whole with `200`. Confirmed on the pin: httpfs
  makes a `HEAD`, then a `GET` with `Range: bytes=0-<size-1>`, and accepts the `200`.
- The inflated length must equal `body_len`.

**Corruption or transport error.** A chunk whose digest differs, or an object that is missing or
shorter than recorded, is corruption. A read that ends early is also what a dropped connection looks
like, so the object's size is asked for before calling it corruption; otherwise it is a transport
error (the response is aborted all the same, and nothing is marked).

**Failure mid-response.** If a chunk fails verification after headers were sent, the reader returns
`ErrCorrupt`. The HTTP handler (spec 0006) must abort the connection
(`panic(http.ErrAbortHandler)`), so a client never sees a clean, truncated file. The record gets
`corrupt_at` (written once per commit, so a bad object does not turn every request into a database
write), a metric and an alert are raised, and the next commit of the body repairs the object.
The store is not trusted, so a bucket writer can deny service but cannot serve a different body.

**Caching.** Records never change except for `corrupt_at`, so serving caches them by
`(domain, body hash)`, for 15 minutes (spec 0016: the collector may delete a record a grace after
nothing references it). Per-request read buffers are never shared.

Spec 0006 limits multi-range requests: each range can pull whole chunks.

## Security

- **Integrity.** Objects are content-addressed. Every served byte is verified against chunk digests
  in the database first. A failure aborts the connection and is repaired on the next commit. The
  database is the trust root.
- **Isolation.**
  - Storage domains are pinned to their stores and marked with the deployment.
  - Overlapping stores are refused.
  - Dedup stays inside a domain and is unobservable, because every commit uploads.
  - Serving takes resolved records, never raw hashes.
- **Credentials:**
  - kista's own providers only, from files;
  - SDK credential chains and steering variables are not used;
  - shared keys and endpoint overrides only in dev on loopback;
  - TLS required off loopback.
- **Exposure:**
  - kista never sets ACLs;
  - it refuses to start when a domain's marker is anonymously readable;
  - the documentation sets S3 Block Public Access and `allowBlobPublicAccess = false`.
- **Resources:**
  - `max_body` and `max_ingests` bound spool disk use;
  - spool files are private, created with `O_EXCL`, removed on every path, and swept at start;
  - reads are bounded by ranges and timeouts.

## Testing

- **Contract suite** (`internal/blob/blobtest`), run by every backend:
  - Put/Get/Stat/Delete/List, with `List` reporting the modification time;
  - ranges at chunk boundaries;
  - a Put that replaces an existing key;
  - refused keys and prefixes;
  - a missing object is `ErrNotFound`;
  - an interrupted Put leaves no visible object;
  - concurrent Puts of one key;
  - a multipart Put (17 MiB), and a cancelled one that leaves nothing visible and no pending upload;
  - a stalled server: every call fails within bounds, a caller's deadline is reported as such;
  - errors without planted secrets, keys, hosts, buckets or prefixes;
  - steering environment variables (`AWS_*`, `MINIO_*`, `~/.aws` via `HOME`) are ignored.
- **Real servers in CI (Linux):**
  - SeaweedFS, pinned by digest, for `s3` with `sse: none` (`make test-s3`). MinIO no longer
    publishes images to Docker Hub or Quay; the suite also passes against a MinIO server;
  - Azurite, pinned by digest (`azurite-blob --skipApiVersionCheck --loose`, the well-known dev
    account; `make test-azurite`) for `azureblob`;
  - run as `docker run` steps, gated by `KISTA_TEST_S3` / `KISTA_TEST_AZUREBLOB` and required with
    `KISTA_TEST_REQUIRE_BLOB=1`;
  - `fs` always; macOS runs `fs` only.
- **Service:**
  - spool, verify, commit;
  - a caller that rejects the file stores nothing and leaves no spool;
  - `max_body`, `max_ingests`, the startup sweep;
  - a dedup hit still uploads, and repairs a planted object;
  - two commits racing, and replicas starting and committing together on all three databases;
  - a dropped connection mid-object is not corruption;
  - the record round trip on all three databases;
  - `OpenGzip` bytes equal spec 0002's `WriteGzip`;
  - a range inside a chunk, a range across chunks, the last bytes;
  - a tampered object byte returns `ErrCorrupt` with nothing of that chunk, and sets `corrupt_at`;
  - plain bytes equal body plus signature, and the length is checked;
  - domain pinning: a changed `store_id`, overlapping stores, a foreign marker, a public marker, a
    tenant with a missing domain.
- **e2e.** A real extension is spooled, verified (footer, test signature) and committed into `fs`,
  then into an S3 server. Served by `http.ServeContent` with a channel signature, DuckDB installs and loads
  it:
  - over `http://` (one `GET`);
  - over `https://` through httpfs (`HEAD`, then a ranged `GET`, with `ca_cert_file`);
  - and with the `.gz` missing, the plain name through httpfs.

  The e2e and CI path filters include `internal/blob/**`.

## Alternatives considered

- **Also store the raw body.** It doubles storage for a path DuckDB almost never takes.
- **Address objects by body hash.** Two compressors would race on one key with different bytes.
- **Skip the upload on a dedup hit.** It leaks whether another tenant stored the body, and it never
  repairs a bad object.
- **gocloud.dev/blob, or minio-go's own credential chain.** Both pull credentials and endpoints from
  the environment, around spec 0004's hardening.
- **The AWS SDK for S3.** minio-go is lighter, Apache-2.0, and speaks to R2 and MinIO directly. AWS
  identity (phase 3) plugs in as a credentials provider.
- **Verify a whole object before serving.** It costs a full read per request. Chunk verification
  stops at the first changed byte at no extra cost.
